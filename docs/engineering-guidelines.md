# 架构与代码规范

本规范适用于当前 v2 实现和审查，配合[设计文档](ai-native-game-engine-design.md)、[v2 契约](framework-v2.md)使用。实际完成范围以[v2 验收](v2-acceptance.md)为准；旧阶段记录保留为历史证据。

目标是让读者从入口顺着代码看清楚：**依赖什么、验证什么、何时修改状态、失败后会发生什么。** 简洁指概念少、路径直接、职责清楚，不以文件数或代码行数最少为目标。

“必须”和“禁止”属于边界要求；“优先”和“建议”允许按实际问题取舍。需要改变边界要求时，应明确记录原因、替代设计和验证证据，并同步更新规范，不能留下隐式例外。

## 1. 架构约束

### 1.1 依赖方向与装配

| 模块 | 可以依赖 | 禁止依赖 |
| --- | --- | --- |
| 内核与核心契约 | 标准库、明确评审过的纯计算依赖 | Unity、具体游戏、宿主、CLI、文件与网络实现 |
| 具体玩法 | 内核契约、已校验的配置数据 | Unity、宿主生命周期、CLI 协议 |
| 共享 Hosting | 内核、明确锁定的 JSON 依赖 | 具体游戏、Unity、文件/网络实现、具体宿主 |
| 游戏协议适配 | 对应玩法、Hosting | 文件/网络实现、具体宿主 |
| Physics / Jolt | 标准库；Jolt 适配可依赖 Physics 与显式原生桥接 | Example、Core 游戏规则、Unity |
| 通用 Headless | Hosting、必要的输入输出适配 | Example、具体物理实现 |
| Example Runner | 宿主、游戏适配、物理工厂 | 绕过公开契约修改内部状态 |
| Unity 表现适配 | 核心公开接口、表现与资源能力 | 核心内部可变状态及独立玩法裁决 |
| CLI 与验证工具 | 宿主公开能力、测试和报告工具 | 绕过边界直接修改玩法状态 |

依赖必须单向，禁止循环引用。核心契约由内核侧拥有；具体玩法实现契约，宿主负责创建对象并注入依赖。首版不要求每个逻辑模块单独建项目，但纯内核与 Unity 必须能独立编译和验证。

- 依赖通过构造函数或明确的调用参数传入。禁止 Service Locator、可变全局单例或隐藏的静态服务访问。
- 模拟实例拥有自己的状态与随机源，不在不同对局间共享可变静态字段。常量和无状态纯函数可以使用 `static`。
- 内核不读文件、不发网络请求、不启动进程、不访问编辑器；宿主完成输入输出，将校验后的数据传入。
- 禁止用反射扫描、自动注册或全局事件总线隐藏主要规则的执行顺序。首版使用显式注册与调用。
- 接口用于真实模块边界、可替换的外部能力或规则扩展点；禁止为每个类机械生成接口。

### 1.2 状态、命令与错误

- 权威状态必须有明确所有者，正常玩法修改只在受控逻辑步中发生。查询不修改状态，属性 getter 不推进模拟或执行输入输出。
- 对外返回副本或真正隔离的只读数据；仅将集合声明为 `IReadOnlyList<T>` 不足以保证元素不可变。不得泄露可变实体或配置引用。
- 命令先验证，再计算，再提交变更并产出事件。预期拒绝不得留下部分扣费、位移、伤害或随机数消耗。
- 管理操作（加载、恢复）使用独立明确入口，校验成功后再替换当前状态。禁止伪装成查询或普通属性赋值。
- 预期业务失败返回明确结果与原因；异常用于不变量破坏或非预期故障。禁止空 `catch`、捕获后返回成功或静默用默认值继续。
- 意外故障导致状态完整性无法确认时，终止该模拟实例的继续推进并报告失败；不能把它当成一次普通命令拒绝。
- 状态提交后发布的事件用于通知结果，不允许表现层回调重新裁决本步规则。事件订阅与释放应有明确生命周期。

当前状态、推进与协议以[v2 契约](framework-v2.md)为准。泛型运行时持有游戏；模块创建完整运行时。Submit仅排队，Advance消费所有输入并推进一个Tick，输入数与Tick分开。游戏回合由规则决定。物理为可选依赖，所有权、原生回调、保存边界和失败清理必须显式验证。

观察、完整快照与表现数据分别处理。表现消费绑定Tick的观察；实时事件不得因覆盖画面帧丢失。重载后Reset使旧回调失效；截图检查指定Tick。跨宿主compare不执行模拟，不放宽恢复门禁。

### 1.3 确定性与复杂度

核心禁止隐式读取系统时间、全局随机源或 Unity 帧时间。顺序必须显式稳定；哈希容器只用于查找，参与规则执行或摘要生成时使用规定顺序。首版模拟串行推进，不用并发任务修改权威状态。

优先组合和直接调用，避免深继承链。不要为单一玩法建设通用规则 DSL、万能组件容器、插件系统或多层转发包装。重复出现且语义一致的逻辑再抽取共享实现；表面相似但演化方向不同的逻辑允许小范围重复。

新增第三方依赖、序列化格式或跨模块公共接口时，在改动说明中写明用途、替代方案与兼容影响。性能优化先测量，保留清晰的行为验证；不为假设性能问题提前引入对象池、缓存或原生代码。

## 2. 代码组织

- 先按责任模块划分，再在模块内按能力组织，例如命令、回放、快照；避免全仓库只有 `Managers`、`Services`、`Helpers` 这类按技术名词堆放的目录。
- 新建目录必须有实际内容和职责，不按架构图提前生成空目录。未来源代码与测试分开存放，测试结构对应被测模块。
- 一个文件通常只有一个主要类型，文件名与类型名一致。紧密关联的小型结果类型可以同文件放置；不为凑规则把一个清晰概念拆散。
- 类型内部按字段、构造函数、公开行为、私有实现组织；有关联的方法放在相邻位置。优先让公开入口先表达完整流程，细节随后展开。
- 公共 API 保持最小可见范围；默认使用 `internal` 或 `private`，仅公开跨边界确实需要的成员。不得仅为了测试扩大生产接口。
- 一个函数完成一个可命名的步骤，尽量保持同一抽象层级；不要把规则判断、磁盘写入与 UI 更新混在一起。

函数超过约 40 行、文件超过约 300 行、控制流超过三层嵌套时，作为人工审查信号，检查是否承担多种职责；这些不是硬性门禁。清晰的规则表或顺序算法可以保留，禁止为了达标拆成大量无意义的一行包装。

## 3. C# 风格约定

以下为本仓库约定，不代表外部语言标准。具体语言版本与目标运行时在创建首个 C# 项目时确认，必须兼顾 Unity 适配；不为使用新语法而升级技术栈。

| 项目 | 约定 |
| --- | --- |
| 格式 | UTF-8、LF、四空格缩进；大括号单独成行，条件和循环体始终加大括号 |
| 命名 | 类型、方法、属性、枚举成员与常量用 `PascalCase`；参数和局部变量用 `camelCase`；私有字段用 `_camelCase`；接口使用 `I` 前缀 |
| 标识符 | 使用完整、常见的英文领域词；避免自造缩写、拼音和含义模糊的 `data`、`temp`、`manager`；小范围循环索引可用 `i` |
| 局部类型 | 右侧明显表明类型时可用 `var`，例如 `new MoveCommand(...)`；读取者需跳转才能判断时写明类型 |
| 空值 | 创建项目时启用可空引用分析；明确可空契约，不以 `!`、任意默认值或关闭警告掩盖未处理的状态 |
| 可变性 | 不变字段优先 `readonly`；公开数据尽量不可变，集合元素的可变性同样需要处理 |
| 异步 | 真正的异步方法使用 `Async` 后缀；异步输入输出留在宿主和工具层，不把串行模拟包装成假异步 |
| 表达式 | 简短无副作用的表达式可使用表达式体；包含验证、分支或状态修改的方法采用块体 |
| 数值 | 规则中的数值应有领域名称或配置来源；带单位的量在名称中体现，如 `timeoutMilliseconds`、`turnIndex` |
| 调用参数 | 易混淆的同类型参数使用命名参数；避免多个布尔开关组合控制行为，优先明确方法或有意义的选项类型 |

命名要揭示行为：`CanMove`、`GetUnit` 不修改状态；`ApplyMove` 表明状态改变；`TryGetUnit` 明确可能没有结果。异步方法也不得隐藏“排队成功”和“执行完成”的差别。

不要在未形成实际用途前创建公共 DTO、异常基类、通用 `Result<T>` 框架或格式化封装。确有多个调用点共享同一语义时，再集中统一，避免多个模块各自发明相互冲突的协议。

## 4. 面向人的可读性

### 4.1 让主流程直接可见

入口方法应按业务发生顺序表达“校验 → 计算 → 提交 → 通知”。失败路径使用清晰的提前返回，避免把正常路径放进多层 `if`。复杂条件提取为有领域含义的变量或函数，避免双重否定、嵌套三元表达式和依赖优先级的长条件。

LINQ 适用于简短、无副作用的数据转换。需要修改状态、保证执行顺序、定位失败或逐步调试时，优先使用明确的循环；不要把伤害结算或状态变更藏在 `Select` 等表达式里。对可能延迟执行的枚举，明确求值时机，避免查询后读取到另一个逻辑步的数据。

下面仅示意局部验证代码的表达方式，省略类型定义，不是完整移动命令实现：

```csharp
// 避免：读者需要自行还原每个缩写和边界含义。
if (x < 0 || y < 0 || x >= w || y >= h || b.Contains((x, y)))
{
    return false;
}

// 推荐：名称表达游戏概念，失败原因可以直接用于诊断。
if (!map.Contains(destination))
{
    return MoveResult.Rejected(MoveError.OutOfBounds);
}

if (map.IsBlocked(destination))
{
    return MoveResult.Rejected(MoveError.Blocked);
}
```

提取函数必须带来可理解的语义。若读懂十行流程必须跳转十个只转发参数的函数，应减少间接层。

### 4.2 注释、文档与诊断

- 注释解释原因、不变量、边界和不直观的算法取舍，不逐句翻译代码。修改行为时同步修改相关注释。
- 领域规则和架构说明优先用清楚的中文；代码标识符保持英文，术语在文档与代码中一致。不要在代码里保留 Agent 对话或生成过程。
- 公共边界的 XML 文档说明副作用、输入限制、失败语义及顺序要求；显而易见的私有成员无需机械补注释。
- 不保留注释掉的旧实现和过期分支。必要的 TODO 写清待解决问题与触发条件，能关联任务时附上引用。
- 错误和日志提供命令类型、实体标识、逻辑步及原因等定位信息。错误码用于机器判断，文本用于人理解，不让调用者解析自然语言日志。
- 测试使用描述场景与期望的名称，例如 `Move_WhenDestinationIsBlocked_LeavesStateUnchanged`；按准备、执行、断言组织，断言重点是行为与不变量。

## 5. 审查与逐步自动化

每次代码审查回答以下问题：

1. 能否从入口和名称看清业务流程，是否需要反复跳转才能知道发生了什么？
2. 依赖是否单向、显式，是否新增了无实际用途的接口、继承或通用框架？
3. 状态由谁修改、何时生效、失败后是否完整，查询是否真正无副作用？
4. 时间、随机数、顺序与外部输入是否受控，现有回放和快照契约是否受影响？
5. 是否有合理的命名、简洁的控制流及必要的原因说明，而不是靠长注释解释复杂代码？
6. 验证是否针对行为，改动是否夹带无关重构，说明是否准确区分已检查与未检查？

已落地 `.editorconfig`、可空分析、编译器检查与只读格式检查，并配置基础 CI 执行。后续用构建引用和必要的架构检查验证核心不依赖 Unity、宿主与具体玩法；用行为测试验证状态与确定性要求。

自动工具处理格式和可检测的错误；职责划分、命名、抽象是否必要和流程是否易读仍由人或独立 Reviewer 审查。不得将行数阈值变成机械拆分要求，也不得将人工审查项描述成已由自动门禁覆盖。
